# Conventions

These are the house rules. New code should look like the code around it.

## Layout and naming

- `api/src/routes/<resource>.ts` exports `<resource>Router(...services): Router`.
- `api/src/services/<entity>Service.ts` exports `class <Entity>Service`.
- `api/src/repositories/<entity>Repository.ts` exports `class <Entity>Repository`.
- `web/src/pages/<Name>Page.tsx` exports `function <Name>Page`, with tests beside it
  in `<Name>Page.test.tsx`.
- Files are camelCase (`appointmentService.ts`); React components are PascalCase.
- API JSON and TypeScript use camelCase. SQL tables and columns use snake_case.
  Repositories own the mapping (`toPatient(row)` and similar).
- API imports use the `.js` extension (NodeNext ESM): `import { x } from './x.js'`.

## Layers

**routes → services → repositories.** Never skip a layer.

- **Routes** read `req.params`, `req.query` (with the helpers in `routes/query.ts`) and
  `req.body`. They call one service method and send its result. Routes contain no
  business logic and no SQL.
- **Services** validate input (helpers in `lib/validate.ts`), enforce business rules,
  and run multi-step writes inside `this.transact(() => ...)`. Services take
  everything they need through their constructor, which is wired in `container.ts`.
- **Repositories** run SQL with prepared statements and return domain objects from
  `domain/types.ts`. No validation and no business rules.

Handlers are synchronous (better-sqlite3 is synchronous). Express 4 catches errors
thrown from synchronous handlers. If you add an `async` handler, wrap it so rejected
promises reach `next(err)`.

## Errors

Every error response has the same shape:

```json
{ "error": { "code": "SLOT_UNAVAILABLE", "message": "This slot is no longer available" } }
```

Throw an `AppError` from a service using the helpers in `lib/errors.ts`. Do not build
error responses in routes.

| Status | Helper                            | Use for                                                |
| ------ | --------------------------------- | ------------------------------------------------------ |
| 400    | `validationError(msg)`            | Malformed input. Code is always `VALIDATION_ERROR`     |
| 404    | `notFound(entity, id)`            | A referenced entity does not exist (`NOT_FOUND`)       |
| 409    | `conflict(CODE, msg)`             | Conflicts with current state (`SLOT_UNAVAILABLE`)      |
| 422    | `businessRule(CODE, msg)`         | Valid input that breaks a rule (`APPOINTMENT_STARTED`) |
| other  | `new AppError(status, CODE, msg)` | Anything else (for example 410 Gone)                   |

Codes are `UPPER_SNAKE_CASE`, specific and stable: clients and tests depend on them.
Messages are for humans and may change. Unhandled errors become 500 `INTERNAL_ERROR`.

## IDs and time

- IDs are opaque strings with a type prefix, generated by `newId('pat')` (`lib/ids.ts`).
- All timestamps are UTC ISO-8601 strings (`2030-01-08T09:00:00.000Z`), stored as TEXT.
  Use `toIso()` when writing and `parseIsoUtc()` / `requireIsoTimestamp()` when reading
  input. ISO strings in this format sort correctly as text, so SQL can compare them.
- **Never call `new Date()` or `Date.now()` for "now" in services.** Inject the `Clock`
  (`lib/clock.ts`) and call `clock.now()`. Tests use `ControllableClock` to freeze and
  advance time.

## Configuration

All environment variables are read in `api/src/config.ts` (`loadConfig`). Add new
settings there with a default, and document them in the README.

## Testing

- **Service tests** (`api/test/<entity>Service.test.ts`) use `createTestContext()`
  from `test/helpers.ts`: an in-memory database with all migrations applied, a frozen
  clock at `NOW`, and helpers to insert providers, patients and slots. Assert error
  cases with `expectAppError(fn, status, code)`.
- **HTTP tests** (`api/test/api.test.ts`) use supertest against `createApp()`.
- Services must stay at 80% or more coverage. `npm test` fails below that.
- **Web tests** render pages with `renderApp(path)` and stub the network with
  `mockApi({ 'GET /path': body })`.
- **E2E** (`e2e/`) runs against the built app with dev routes enabled. Each test starts
  with `POST /api/dev/reset` and sets the clock with `POST /api/dev/clock`.

### Test IDs

Every interactive element (links, buttons, inputs, selects) and every element a test
needs to read gets a `data-testid`:

- kebab-case, prefixed by the page or feature: `booking-submit`, `patient-name-input`.
- Per-row elements append the entity id: `slot-book-${slot.id}`,
  `appointment-row-${appointment.id}`.
- Shared elements: `error-banner` (from `<ErrorBanner>`), `nav-*` for navigation.

Test IDs are a public contract. Do not rename existing ones.

## Dev routes (test hooks)

`/api/dev/*` (mounted only when `ENABLE_DEV_ROUTES=1`, in `routes/dev.ts`) contains
hooks for automated tests: reset the database, and freeze or advance the clock. When a
feature needs a hook for testing, such as a way to inspect messages a stub sent or to
trigger time-based processing, add it as a dev route or as an explicitly specified
endpoint. This counts as part of the feature, not scope creep. Keep
`POST /api/dev/reset` working: it discovers tables at runtime, so new tables are
covered automatically.

## How to…

### Add a migration

1. Create `api/migrations/NNN_short_description.sql` with the next number
   (`002_add_reminders.sql`). Use lowercase letters, digits and underscores only.
2. Write plain SQLite DDL. Use TEXT ids, `*_at TEXT` UTC timestamps, and
   `REFERENCES` for foreign keys (enforced: `foreign_keys = ON`).
3. Never edit a migration that has been committed. Add a new one.
4. Migrations run automatically on API startup and in `createTestContext()`. The runner
   records applied files in `schema_migrations`, so each file runs once.
5. Add a test in `api/test/migrate.test.ts` if the migration has constraints worth checking.

### Add an API route

1. Add types to `domain/types.ts` if you need new ones.
2. Add a repository method (SQL) and a service method (validation, rules, `transact`).
3. Wire new classes in `container.ts` and add them to `Services`.
4. Add the handler to an existing router, or create `routes/<resource>.ts` and mount
   it in `app.ts` under `/api`. Staff-only operations go under `/api/staff`.
5. Test the service in `api/test/` and at least the happy path and one error over HTTP.
6. Add the endpoint to the API table in the README.

### Add a page

1. Create `web/src/pages/<Name>Page.tsx` and add a `<Route>` in `App.tsx`.
2. Add a `NavLink` with `data-testid="nav-<name>"` in `components/Layout.tsx` if users
   should navigate to it.
3. Add client functions to `web/src/api/client.ts` and types to `web/src/api/types.ts`.
4. Load data with `useApiData`. Show failures with `<ErrorBanner>`. Use
   `useCurrentPatient()` for the patient being acted for.
5. Add `data-testid`s as described above, and a `<Name>Page.test.tsx`.
